# Document configuration: label and value sources

Checked against the current client code on `integrate/b2b-plus-gokul-dev` and the five captured admin configurations, 29 September 2026. This file documents the implemented print behavior; it does not change any configuration or backend data.

**Read each row as two separate things:** the document configuration chooses the caption/text and visibility; store, customer, sale and return records provide business values. Some rows are free text or switches, so they have no separate business value. Changing document language does not translate addresses, customer names, bank names or numbers automatically.

PDF and thermal renderers keep captions and business values in separate text
runs, including mixed captions such as `Tel Phone عربي`. Numbers and dates
retain their own direction, and narrow fields wrap rather than insert a value
inside its caption. See the [rendering fix report](receipt-mixed-script-rendering-fix-2026-09-29.md).

## Which document configuration is selected?

| Print request | Primary document configuration | Where English / Arabic text comes from |
| --- | --- | --- |
| Sales thermal (58/80/112 mm) | **Bill — 1102** | Its display options received from the API. |
| Sales A4 / A5 PDF | **Bill A4 — 802**, falling back to Bill if unavailable | Its display options received from the API. |
| Combined sales + returns thermal | **Sales and Return Bill — 27**, falling back to Bill | Main sale/return columns and final-summary captions belong to this primary configuration. Return metadata may use a secondary configuration; see below. |
| Combined sales + returns A4 / A5 PDF | **Sales and Return Bill A4 — 843**, then combined thermal configuration, then Bill A4, then Bill | Same main-field rule, with the selected primary configuration. |
| Return-only thermal or PDF | **Return Bill — 28**, falling back to Credit Note when Return Bill is unavailable | Return Bill is passed as both the primary and return configuration. |

These IDs identify the tested tenant records; the client selects by document type, not by hardcoded ID. Paper size and the request select the document type first; that document's `language` selects language handling. A theme named “English” or “Bilingual” does not replace this language rule.

**There is no client-side second lookup of a separate English document for every bilingual field.** The client consumes `display_configuration.<key>.value` and `.default` from the selected API record. If the backend combines an English template into `.default`, that combination has already happened before rendering; this client does not prove that backend mapping.

## Exact language rule used by the tables

| Field behavior | English | Arabic | English + Arabic |
| --- | --- | --- | --- |
| Ordinary configured label | First nonempty text without Arabic script: option **`default`**, then **`value`**, then supplied resolved English/non-Arabic resolved text, then the renderer's English fallback. English-only edits may arrive in `value`. | Option **`value`** first, then supplied Arabic `resolved_labels` text, then Arabic fallback. A nonempty `value` is retained as typed; it is not automatically translated or rejected for using Latin text. | **`value` is the Arabic slot; `default` is the English slot.** Print Arabic and typed English when both exist. Print only the filled slot when the other is empty. Equal texts are printed once. |
| Both configured label slots empty | Use the English resolved/built-in fallback where available. | Use the Arabic resolved/built-in fallback where available. | Prefer the Arabic resolved/built-in fallback. Do not add an English master/default label merely because one exists. Empty free-text fallbacks can leave the row empty. |
| Clear the English template field | English-only rendering may still use a non-Arabic `value` or an English fallback. | Arabic field remains the source. | `.default` empty means **no English line for that key**; Arabic remains. Selected English table fields appear only for the corresponding keys whose `.default` is filled. |
| Layout placement | Caption/value in the English part of the layout. | Caption/value in the Arabic part; Arabic-only item tables reverse their column presentation. | Arabic then English, or separate language cells depending on the theme. A layout may repeat the same business value next to both captions; it does not fetch two different values. |
| Visibility | Own switch must be explicitly true; parent block/data conditions still apply. | Same switches and data conditions. | Same switches and data conditions. Empty English text is different from turning the field off: the latter hides its content in both languages. |

`default` above is the actual JSON key parsed into `DisplayOption.defaultValue`; it is not `default_value`. `resolved_labels` contains fallback captions, not actual customer or financial values. The English resolved fallback is used only when the caller supplies it. In particular, Return metadata helpers do not automatically copy every `resolved_labels.*_default` into the bilingual English slot.

In the following tables, **configured English** and **configured Arabic** mean this exact rule, with the option key shown at the left. “Value” describes its source, not a sample test value. All figures keep their business meaning across languages.

## Return and combined metadata that are not ordinary display-option rows

The combined print entry points in `print.dart` currently choose a secondary **Credit Note first, then Return Bill**. Its metadata may supply headings and credit-note/customer captions, while combined return item columns and final totals still belong to the primary combined document. If no secondary configuration is passed, shared section helpers fall back to the primary document. Return-only printing instead explicitly prefers **Return Bill**. Do not assume a combined credit-note heading always comes from configuration 28.

The primary printed document's language controls these secondary captions too. Merely setting the secondary record to Arabic does not independently switch the combined receipt's language.

## Data-source and fallback details

| Source | What is actually used |
| --- | --- |
| Store details | `StoreSessionProvider.resolveActiveStore()` supplies location/phone/email for normal print entry points. A provided store name is passed as `storeName`; Return builder resolves the active store name directly. Phone/email can fall back to application customer-care settings. None of these values come from the address/telephone/email caption text. |
| Store registration | Cached ZATCA VAT, CR and company-name settings, passed into `ReceiptLayoutParams`. The supplier company row uses ZATCA company name, not the configured store-heading text. |
| Bank selection | `BankProvider.banks`: first active bank with accounts, else first bank with accounts, else first bank. Its primary account is the first active account, else first account. Missing bank/account values omit their rows. |
| Sale/order data | Print-call params from order/local-cart data: customer, date, reference, token, payment, balances, delivery, comments, totals and line values. For an explicit sales-only-after-return action, `buildSalesOnlyCartItems` adjusts remaining quantities and scales tax/line totals; this is business data preparation, not language selection. |
| Return data | `OrderReturns.returnItems` and `returnTotalAmount`; original sale lines can supply a price/MRP fallback. Original invoice reference/date remain separate from return reference/date. |
| Return price priority | Finite explicit returned `unitPrice` wins, including zero. Explicit returned MRP then falls back to that rate. Otherwise match original cart line by cart-item ID, or product name and variant, and use its unit price/MRP. Last legacy fallback is refund total divided by returned quantity for both rate/MRP. |
| Return refund priority | Finite explicit `returnTotalAmount` wins, including zero. Otherwise sum returned quantity × resolved return rate. This resolved total feeds return total, refund, QR total and words where those fields render. |
| Return allocated tax/subtotal/discount | Explicit return allocations only. Unknown/invalid values remain blank. Aggregate allocated totals require every returned line to have the corresponding finite allocation. Original sale tax/discount and builder placeholder values do not fill missing return allocations. |
| Sold product-name language | English uses `names.en` / available product name. Arabic uses supplied Arabic name if available, otherwise English/product name. Bilingual uses Arabic then English if Arabic exists. Variant attributes accompany the primary name. Clearing English configured captions does not remove English product names. |
| Returned product-name language | Shared returned-item path uses supplied `OrderReturnItem.productName` and variant attributes directly in all modes. A configured Arabic particulars caption does not translate that return name. |
| Business-value language | Store/customer/bank names, addresses, reference numbers, HSN and unit names are printed from source data; there is no generic translation of them. Only sold-product names, generated words and selected renderer-owned payment names have explicit language behavior. |
| Configuration cache | `DocumentConfigProvider` consumes the API configuration map and cached Hive / SharedPreferences snapshots. A saved admin edit must reach that response/cache before the renderer can use it. The renderer does not scrape the admin form. |
